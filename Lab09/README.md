## Завдання 3. Відповідь на питання завдання 3 ($c = 1$)

**Питання:** Сортування вставками з бінарним пошуком позиції зменшило кількість порівнянь, але переставлянь залишилося рівно стільки ж. Чому це не дало виграшу в часі?

**Відповідь:**  
Бінарний пошук точки вставки скорочує кількість порівнянь ключа з $O(n^2)$ до $O(n \log n)$. Проте головним пляшковим горлом (bottleneck) для алгоритму вставок є **фізичний зсув елементів масиву праворуч** (`a[j] = a[j-1]`), кількість яких залишається квадратичною — $O(n^2)$ записів у пам'ять. Оскільки операції запису та копіювання в оперативну пам'ять/кеш є значно дорожчими за скалярні порівняння чисел у регістрах CPU, саме $O(n^2)$ операцій зсуву домінують у часі виконання і не дозволяють прискорити алгоритм на великих обсягах даних.

### Обґрунтування властивостей алгоритмів за даними таблиці:
1. **Сортування вибором:** Кількість порівнянь однакова у всіх чотирьох колонках і суворо дорівнює $\frac{n(n-1)}{2}$ (4950, 499500, 49995000). Кількість переставлянь на відсортованому масиві дорівнює `0`, оскільки перевірка `minIdx != i` виключає зайві обміни.
2. **Сортування злиттям знизу вгору:** Кількість переставлянь **абсолютно однакова** для всіх типів входу при фіксованому $n$ ($2 n \lceil \log_2 n \rceil$, тобто 1400 для $n=100$, 20000 для $n=1000$ і 280000 для $n=10000$), оскільки буфер заповнюється і копіюється на кожному рівні злиття незалежно від порядку елементів. Кількість порівнянь має порядок $O(n \log n)$.
3. **Бінарними вставками:** Кількість порівнянь є стабільно низькою для всіх типів входу ($\approx n \log n$), але кількість переставлянь (зсувів) кардинально варіюється: від $n-1$ на відсортованому вхідному масиві до $\approx \frac{n^2}{2}$ на зворотно відсортованому.

## Завдання 6. Висновок та відповіді на питання

1. **Відношення порівнянь простого та швидкого алгоритмів на $n = 10\,000$ проти 376 з лекції:**  
   У нашому випадку для $n = 10\,000$ сортування вибором виконує $49\,995\,000$ порівнянь, а сортування злиттям — $123\,577$ порівнянь. Відношення складає $\frac{49\,995\,000}{123\,577} \approx 404.5$.  
   Лекційне число 376 розраховувалося для алгоритму **QuickSort** при теоретичній кількості порівнянь $n \log_2 n \approx 132\,877$. Оскільки сортування злиттям (Merge Sort) має іншу кількість порівнянь при злитті двох підмасивів і розбитті на рівні, отримане реальне відношення $404.5$ є абсолютно точним для даної теми.

2. **Чому `Array.Sort` швидший за власний $n \log n$ алгоритм (дві причини без слів «краще оптимізований»):**  
   * **In-place алгоритм без копіювання у буфер:** `Array.Sort` використовує Introsort, який не потребує додаткової пам'яті. Наше сортування злиттям на кожному кроці змушене виділяти пам me'ять та виконувати у 2 рази більше записів ($2 n \log n$ операцій запису у `temp` і назад).
   * **Інлайнінг порівнянь без виклику делегатів:** `Array.Sort` для базових типів (таких як `int`) використовує спеціалізовані інструкції машинного коду без overhead на виклики делегата `cmp(x, y)` через вказівник на кожній ітерації.

3. **Вибір алгоритму для задачі (100 000 записів, ключі 0–300, щодня, стабільність):**  
   Найкращим вибором є **Сортування підрахунком (Counting Sort)**. Оскільки діапазон ключів надзвичайно вузький ($M = 301$, цілі числа від 0 до 300) при значному обсязі елементів ($N = 100\,000$), сортування підрахунком виконується за лінійний час $O(N + M)$ за один прохід (в десятки разів швидше за будь-який $O(N \log N)$ алгоритм), а його класична реалізація з обходом з кінця гарантує 100% стабільність.
